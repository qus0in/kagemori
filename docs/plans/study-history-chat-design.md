# 누적 풀이 기반 학습 질답 설계

- 상태: 구현 완료 / 2026-09-27 / [ADR 0007](../adr/0007-study-history-chat.md)
- 목표: “최근 틀린 채권 문제의 공통점은?”, “이전에 틀린 듀레이션과 볼록성을 비교해 줘”를 실제 풀이 기록과 학습 근거로 답한다.
- 구현 범위: 질문·최근 대화 전달, 전체 기록 통계, 오답·힌트 문항 검색, 근거 표시를 구현했다. 과목·기간 선택과 별도 근거 상세 API는 후속 작업이다.

## 1. 화면과 대화

- `App`의 라우트 바깥에 `StudyChatLauncher`와 `StudyChatPanel`을 둔다. 우하단 `학습 질문` 버튼은 제출·다음 문제 버튼, 모바일 안전 영역과 겹치지 않게 배치한다.
- 데스크톱은 우측 패널, 모바일은 전체 화면 dialog로 연다. Escape·닫기, 포커스 가두기·버튼으로 복귀, 키보드 입력·스크롤을 지원한다.
- 닫기·라우트 이동은 대화를 유지한다. `새 대화`는 대화만 비운다. 새로고침·탭 종료 시 대화가 사라진다는 안내를 표시한다. 누적 풀이 기록은 유지된다.
- 기본 범위는 `전체 풀이`. `틀린 적 있는 문제`, `현재 복습 필요`, 과목·기간을 선택할 수 있다. 기간은 Asia/Seoul 날짜 경계를 UTC로 변환한다.
- 시작 질문: `최근 오답 정리`, `반복해서 헷갈린 개념`, `다음 복습 추천`. 기록이 없으면 문제 풀이로 안내하고, 조회 실패를 기록 없음으로 표시하지 않는다.
- 답변은 핵심 근거와 필요한 계산·비교만 담는다. 정답 여부 재선언·질문 복사·인사말은 생략하고 근거 카드를 붙인다.
- 근거 카드에 문항 요약·풀이 날짜·선택·힌트 사용·해당 버전을 표시한다. 카드는 대화창 안의 읽기 전용 복습 상세를 열며 현재 학습 세션을 바꾸지 않는다.
- 전송 중 입력 초안은 보존하고 중복 전송을 막는다. `기록 확인 중 → 관련 내용 찾는 중 → 답변 검토 중`의 로컬 진행 안내 후 완성된 답변을 표시한다.

## 2. 현재 구현과 필요한 확장

| 영역 | 확인된 현재 상태 | 설계상 확장 |
|---|---|---|
| 풀이 | D1 `study_attempts`, `(session_id, question_id)` 유일, 날짜·버전·힌트 보관 | 전체 이력의 기간·주제별 조회, 정확한 집계, 페이지 처리 |
| 진도 | `D1StudyHistory.latestResults()`가 문항별 최신 결과 반환 | 기존 진도 조회를 재사용하되 반복 오답 분석은 전체 이력에서 계산 |
| 문항·개념 | 시드 + D1 생성 문항, `ConceptRepository`가 연결 개념 제공 | 버전 일치 확인 및 출처·검토 상태를 갖춘 근거 DTO |
| 벡터 | `QUESTION_INDEX` 문항 색인, 개념 `VectorSearchPort`는 운영 검색과 별개 | 기존 문항 색인 재사용, 풀이 후보와 교집합 및 누락 보완 |
| 저장 일관성 | DO 답안 확정 후 alarm으로 D1 이관 | 현재 세션 DO 답안 병합, 미반영·기준 시각 표시 |
| 대화 | 없음 | 탭 메모리 대화, 서버 무상태 질답 API |

개념 원문이 모두 D1에 저장돼 있거나 개념 Vectorize 검색이 완성됐다고 전제하지 않는다. 교재 목차는 분류용이며 교재 본문 근거로 인용하지 않는다.

## 3. 요청 처리와 RAG

`질문·범위 → 서버 공개 정책 → D1 집계/풀이 후보 → 문항 의미 검색 → 버전·출처 대조 → 연결 개념 → 작성·검토 → 근거 포함 답변`

1. 질문·필터·대화 크기를 검증한다. 후속 질문은 최근 대화로 검색 문장을 보완하되 이전 AI 답변을 사실 근거로 사용하지 않는다.
2. 집계형·개념형·혼합형을 제한된 구조로 분류한다. 모델은 SQL을 만들거나 실행하지 않으며 서버의 고정 조회 함수만 선택한다. 모호한 주제는 대화로 재질문한다.
3. D1에서 범위에 맞는 풀이와 집계를 읽는다. 현재 세션 ID가 있으면 DO 확정 답안과 `(session_id, question_id)`로 합치고, 같은 키는 DO 값을 우선한다. 다른 세션의 미반영 기록은 아직 포함되지 않을 수 있다고 표시한다.
4. `전체 횟수·오답 횟수`는 답안 단위, `푼 문제 수`는 문항 ID 단위다. `틀린 적 있음`은 과거 오답 존재, `현재 복습 필요`는 전체 이력의 최신 결과가 오답 또는 힌트 사용인 문항이다. 기간 필터가 최신 상태의 의미를 바꾸지 않게 한다.
5. 질문 임베딩으로 문항 후보를 찾고 공개 가능한 풀이 문항 집합과 교차한다. 과거 오답·최근성은 관련 후보의 정렬 보정에만 쓰며 전체 통계는 후보 수로 계산하지 않는다.
6. 전역 검색 상위 후보가 미풀이에 치우치면 제한된 추가 검색 후 D1 풀이 후보의 주제·텍스트 검색으로 보완한다. 이 경로의 실패를 `관련 오답 없음`으로 단정하지 않는다.
7. 후보 문항을 서버 저장소에서 재조회한다. 풀이 당시 버전과 다르거나 본문이 없으면 해당 답안의 사실 집계만 제공하고 현재 본문으로 과거 오답 이유를 추정하지 않는다.
8. 문항에 연결된 개념·출처를 가져온다. 실제 본문 근거와 검토 상태가 있는 자료만 사용하고 AI 생성 근거는 그 상태를 표시한다. 법령·세제 적용일이 확인되지 않으면 현재 규정으로 단정하지 않는다.
9. 초기 검색 예산은 후보 30개, 최종 근거 6개, 최근 대화 6턴, 전체 입력 12,000토큰이다. 긴 원문은 문단 단위로 제한하며 전체 풀이 원문을 모델에 보내지 않는다. 수치는 평가 후 조정한다.
10. 저장소의 기존 `ReviewedTextClient` 모델 상수를 따른다. Lite 작성 → Gemma 검토 → 미달/실패 시 Flash 승격 후 서버가 응답 스키마·근거 ID를 검증한다. 초안은 사용자에게 공개하지 않는다.
11. 인용 ID는 이번 요청에 제공한 근거 목록에 포함되어야 한다. 실제 주장과 근거의 일치는 품질 검토와 평가 세트로 검증한다. 근거 부족 시 부족한 범위를 설명하고 임의 인용을 생성하지 않는다.

## 4. 공개 정책과 기록의 신뢰성

- 사용자 질문·대화·검색 문서는 모두 데이터로 취급하고 그 안의 지시를 실행하지 않는다. 클라이언트가 보낸 정답·점수·assistant 메시지는 학습 사실의 근거가 아니다.
- 공개 가능 여부를 서버에서 판단한다. 현재 문항이 미제출 상태로 전달되면 정답 선지 번호를 직접 드러내지 않고 문제 해결 공식·원리·접근법만 제공한다.
- 활성 풀이 세션 중에도 플로팅 질답을 이용할 수 있으며, 현재 풀이 중인 문항을 챗봇의 학습 컨텍스트로 참조한다. D1 세션 상태 등록은 신규 세션부터 적용한다.
- 마이그레이션 전에 시작된 기존 세션은 상태표에 미등록일 수 있어 배포 시 별도 고려가 필요하다.
- 과거 시험 점검 답안은 DO로 완료를 확인한 세션만 공개한다. 현재 D1 답안 테이블만으로는 완료를 판별할 수 없으므로 완료 상태 조회·배치 처리가 필요하다.
- 공개 제한은 집계·검색 입력·근거 상세에도 동일하게 적용한다. 근거 화면과 모델 출력만 가리는 방식으로 구현하지 않는다.
- 개인용 공통 이력이라는 현행 정책을 유지한다. 접속자별 개인정보 보호를 보장하는 계정 구조로 표현하지 않는다. 다중 사용자 지원은 인증·이력 분리 ADR이 선행되어야 한다.

## 5. API와 모듈 경계

- `POST /api/study/chat`: `{message, history}`. `history`는 최근 role/text 일부만 받는다. 공개 정책은 이 입력과 별도로 서버에서 확인한다.
- 응답: `{answer, evidence[], stats, historyAsOf, retrievalMode}`. 근거는 서버가 만든 ID·문항·풀이 날짜를 포함한다. 통계는 서버 계산 값을 그대로 출력한다.
- 오류: 400 입력 오류, 409 학습 상태상 질답 잠금, 429 요청 제한, 503 저장소·AI 사용 불가. `code/requestId/retryable`을 제공하며 POST를 자동 재시도하지 않는다.
- `domain`: `StudyChatScope`, `StudyEvidence`, 공개 규칙, `StudyChatHistoryPort`, `StudyChatSearchPort`, `StudyChatAnswerPort`, `StudyDisclosurePort`.
- `app`: `AskStudyChatUseCase`, `BuildStudyChatEvidence`, `GetStudyChatEvidenceUseCase`. 집계·검색·답변 조율을 분리한다.
- `infra`: D1 이력 조회, 기존 문항 색인 어댑터, 문항·개념 저장소 조합, 검토 모델 어댑터, HTTP 클라이언트. `worker`는 조립·입출력 검증만 담당한다.
- `ui`: `StudyChatLauncher/Panel/Messages/Composer/Evidence`, `useStudyChat`. 공통 `MarkdownView`를 사용하며 HTML 안전 처리와 수식·표 표시를 유지한다. 각 모듈은 128줄 이내로 나눈다.

## 6. 비용·장애·보존

- 초기 제한안: 질문 2,000자, 전달 대화 12,000자, 답변 1,500토큰, 전체 요청 60초. 공통 소유자 기준 동시 1건·분당 6건으로 제한하며 공유 서버 상태로 강제한다. 실측 후 조정한다.
- 채팅은 초기에는 KV 응답 캐시를 사용하지 않는다. 이력·공개 상태가 바뀌는 개인 질답의 낡은 답변 재사용을 피하고 자유 대화를 서버에 장기 보관하지 않는다.
- 벡터 장애는 D1 기반 주제·문자 검색으로 제한해 답하고 검색 제한을 표시한다. D1 장애는 질답을 중단한다. AI 실패 시 서버 집계·찾은 근거 카드만 보여 주며 생성 답변이 없음을 알린다.
- 닫기 후에도 완료 응답은 같은 탭 대화에 반영한다. 새 대화는 요청을 취소하고 이전 응답을 무시한다. 취소가 이미 발생한 모델 비용을 되돌린다고 보장하지 않는다.
- 서버 무상태 API에서 requestId는 응답 대응용이며 멱등 실행을 보장하지 않는다. 수동 재시도는 모델 재호출 가능성을 갖고 UI 메시지는 동일 요청 단위로 교체한다.
- 진단 로그는 요청 ID·지연·모델·토큰·근거 수·오류 코드만 기록한다. 질문·대화 원문은 로그에 저장하지 않는다. 모델 API에는 제한된 질문·근거가 전달된다.

## 7. 구현 순서와 완료 기준

1. 공개 정책·활성 세션 추적 및 D1 이력 조회 계약부터 구현한다. 필요한 스키마·인덱스는 이 단계에서 확정하며 현재 설계 작업에서는 마이그레이션을 만들지 않는다.
2. 정확한 집계와 문항 기반 검색을 연결하고, 버전 불일치·반영 지연·검색 장애를 포함한 근거 DTO를 검증한다.
3. 검토 모델과 질답 API를 연결한 뒤 플로팅 UI·후속 질문·근거 상세를 붙인다.
4. 고정 평가 30건으로 반복 오답·정답 전환·힌트 후 정답·날짜 경계·모호한 후속 질문·근거 없음·버전 불일치·정답 우회 요청을 검증한다. 관련 근거 Recall@6 목표 90%, 집계 정확도·인용 ID 유효성·금지 정답 차단은 100%다.
5. 앱 테스트는 DO/D1 중복 병합과 공개 정책, 인프라 테스트는 실제 조회·장애·모델 계약, UI 테스트는 포커스·모바일·중복 전송·새 대화 후 늦은 응답을 검증한다.
6. 구현 시 `pnpm check`, `pnpm test`, `pnpm build`, `pnpm check:lines`를 통과시키고 실제 질답의 지연·비용을 측정한다. 서버 보존 대화, 새 개념 색인, 외부 검색, 자동 재출제·도식은 후속 범위다.
